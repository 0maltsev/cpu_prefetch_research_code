# ADR-0173: Stage 17 cpu-prefetch-v5 CPU-pair identity

- Status: `ACCEPTED`
- Date: 2026-10-20
- Decision ID: D-173
- Classification: platform-dependent topology mapping
- Decision owners: repository owner; platform, controller, timing, queue-correctness, storage, security, and custody owners at their later gates
- Protocol version: `2.0.0-pre.3`
- Supersedes: none; extends ADR-0043's pair-identity approach to a second, independently topology-verified stand. ADR-0043's own pair identity (`XEON-CPU-FETCH-P0-NEAR-0-1-FAR-0-26-v1`) remains valid under its own identity for the decommissioned stand it was verified against; it is not reused or relaxed here.
- Lifecycle gate: software topology proposal only; does not itself populate any CPU set or authorize any real MSR operation

## Context and scientific constraints

ADR-0172 (accepted, `docs/decisions/0172-...md`) registered a new hardware-prefetch-control mapping for CPUID family 6 model `0x3E` (Ivy Bridge-EP, the current real stand `cpu-prefetch-v5`), but deliberately left its CPU set unassigned (`std::nullopt` in `kHardwarePrefetchMappings`), fail-closing every code path that would need one. That ADR's own authority boundary is explicit that ADR-0043's pair-identity decision governs the CPU set separately, and that reusing ADR-0043's own `{0, 1, 26}` triple on different silicon without fresh topology evidence would be inventing a platform-dependent value. This ADR supplies that fresh evidence and proposes the resulting pair identity for `cpu-prefetch-v5`.

Real, read-only topology evidence gathered directly on `cpu-prefetch-v5` (94.126.205.83) this session, not assumed, and captured as the hashed, append-only evidence bundle `docs/evidence/stage17/STAND-TOPOLOGY-CPU-PREFETCH-V5-20261020-01/` (manifest SHA-256 `d1a1234d9b195a17e7765bfbf6100a3f62a1828ad94440df4ef5b5600da8af4c`, independently re-verified file-by-file against `SHA256SUMS` after transfer, not just trusted from the remote capture): `lscpu -e --json`, `lscpu --caches --json`, `numa-node{0,1}-cpulist`, and per-CPU `thread_siblings_list`/`physical_package_id`/`core_id`/LLC `shared_cpu_list` for CPUs 0, 1, and 8. Findings: the stand is dual-socket, 2 NUMA nodes (node 0 = CPUs 0-7,16-23; node 1 = CPUs 8-15,24-31), 16 physical cores with hyperthreading (32 logical CPUs total), one L3 (LLC) domain per socket. CPU 0's hyperthread sibling is CPU 16 (not CPU 1); CPU 0 and CPU 1 are distinct physical cores (`core_id` 1 and 2 respectively) sharing the same L3 `shared_cpu_list` (`0-7,16-23`) and the same `physical_package_id` (0) -- same NUMA/LLC/package domain. CPU 8 has a different `shared_cpu_list` (`8-15,24-31`) and a different `physical_package_id` (1) -- crosses package, NUMA, and LLC domains relative to CPU 0. `numactl --hardware` (captured separately, consistent with the bundle) confirms asymmetric NUMA distance (local 10, remote 21). CPUID identity re-confirmed from `/proc/cpuinfo`: family 6, model 62 (`0x3E`), stepping 4, matching ADR-0172's registered model exactly.

This provides no dynamic qualification or performance result, and authorizes no code change or real hardware operation.

## Options considered

- Worker pair: `(0,1)` near and `(0,8)` far, mirroring ADR-0043's own "keep producer home fixed, vary only the consumer by placement" convention; a different producer CPU; a different far CPU elsewhere in node 1; remain unresolved pending a dedicated topology study.
- Reuse ADR-0043's own pair identity unchanged (`{0,1,26}`) on the assumption the same logical CPU numbers mean the same thing on different silicon. Rejected: CPU 26 on `cpu-prefetch-v5` is a real, valid, online CPU (package 1, core_id 3, independently re-checked directly via `/sys/devices/system/cpu/cpu26/topology/{core_id,physical_package_id}` and `/sys/devices/system/cpu/cpu26/online`), so this wouldn't even fail loudly -- it would silently run a "far" measurement on a CPU chosen without this stand's own topology evidence behind it, precisely the hazard ADR-0172 was written to avoid.
- Block entirely pending a more exhaustive topology study (e.g. microbenchmark-validated cache-latency confirmation beyond sysfs topology). Rejected as the default path: sysfs topology evidence (NUMA node, physical package, LLC `shared_cpu_list`, core id, hyperthread siblings) is the same class of evidence ADR-0043 itself relied on for the original stand ("hashed read-only topology evidence"), not a lower standard.

## Decision

Propose pair identity `CPU-PREFETCH-V5-P0-NEAR-0-1-FAR-0-8-v1`: producer CPU 0 for both placements, consumer CPU 1 for `NEAR`, and consumer CPU 8 for `FAR`. This mirrors ADR-0043's own structure exactly (fixed producer home, placement-driven consumer) and changes only the concrete CPU numbers, backed by this stand's own real topology evidence rather than the prior stand's.

This ADR does not itself populate `kHardwarePrefetchMappings`'s `06_3EH` entry's `control_cpus`, nor authorize any real MSR read, write, probe, or restoration on `cpu-prefetch-v5`. Per ADR-0172's own authority boundary, that requires this ADR (or a revision of it) to be formally accepted first, followed by the exact hash-bound Q15 authorization ADR-0049/ADR-0172 already require.

## Consequences and compatibility

The producer home remains fixed (CPU 0) while the placement factor changes the consumer context (CPU 1 near, CPU 8 far), exactly as ADR-0043 established. Pair-specific clock, affinity, address-residency, atomic, and platform qualification remain mandatory and have not been performed -- this ADR provides topology identity only, not dynamic qualification. Changing either CPU changes the pair identity and invalidates all pair-bound evidence, same as ADR-0043's own rule.

If accepted, the real code change this enables is narrow and already anticipated by ADR-0172's design: populate `kHardwarePrefetchMappings`'s `06_3EH` entry's `control_cpus` with `{0, 1, 8}`, removing the `HWP-CPU-SET-UNASSIGNED`/`S17-Q15R-CPU-SET` fail-closed gates for this model. No other code changes are implied -- the mapping ID, MSR address, mask, and H0/H1 semantics are already registered and unchanged.

## Verification and acceptance tests

- Exact near/far pair test for `cpu-prefetch-v5` (analogous to the existing `HardwarePrefetchMapping.RegistersIvyBridgeEpAsDistinctSiblingMapping`/`IvyBridgeEpFailsClosedOnMissingCpuSet` tests, which would need updating once a CPU set is populated).
- A real Q15-R/Q15-W qualification run on `cpu-prefetch-v5` using this pair is the actual dynamic evidence that would validate it, exactly as ADR-0043's own pair was validated by the original stand's first real Q15-R/Q15-W run, not by topology review alone.

## Rollback or supersession

Stop before any real MSR operation on any topology mismatch and retain diagnostic evidence. Never substitute another CPU on this stand without fresh topology evidence. A change needs a prospective superseding ADR, new identity, and complete pair-/runner-bound requalification; ADR-0043's own evidence remains valid under its own identity for the stand it was verified against.

## Protocol-amendment assessment

This selects a platform/engineering mapping at a delegated gate without changing the imported logical schedule, queue, timestamp, storage, lifecycle, or analysis semantics. No protocol amendment is required, consistent with ADR-0043's own assessment.

## Authority boundary

This document proposes a pair identity and the real topology evidence gathered to support proposing it; it does not itself approve the identity, authorize any code change, or authorize any real prestate read, privileged write, probe, or restoration on `cpu-prefetch-v5`. Acceptance by the real repository/platform/controller/security owners, followed by the real code change described under "Consequences and compatibility" and a real Q15-R/Q15-W qualification run, remain necessary before any real hardware operation under this mapping may proceed.

## Implementation note 2 (runner/qualification worker-pair admission)

A second, independent hardcoding was found while preparing for the real Q15-R/Q15-W run: the runner/qualification subsystem's own worker-pair admission (`include/cpu_prefetch/runner/runner.hpp`'s `kNearWorkerPair`/`kFarWorkerPair` and `kCpuPairSelectionId`, ADR-0043's domain, not ADR-0049/0172's) was still exclusively bound to the decommissioned stand's pair (`{0,26}`, `XEON-CPU-FETCH-P0-NEAR-0-1-FAR-0-26-v1`), with no path to recognize this ADR's own `{0,8}`/`CPU-PREFETCH-V5-P0-NEAR-0-1-FAR-0-8-v1`. Any real Q15-R/Q15-W admission ticket using cpu-prefetch-v5's real far pair would have been rejected here even after the MSR-mapping fix.

Completed: `runner.hpp` gained `kFarWorkerPairV5{0,8}` and `kCpuPairSelectionIdV5`, plus two membership-check functions (`is_accepted_worker_pair`, `is_accepted_cpu_pair_selection_id`) mirroring `kHardwarePrefetchMappings`'s own registry philosophy (a small, explicit, auditable set of registered pairs, not a dynamic runtime lookup in the measurement hot path). `runner.cpp`'s two admission-ticket validation sites, `src/qualification/q15_collectors.cpp`'s and `src/runner/qualification.cpp`'s own two-way pair checks, and `tools/q15_clock_qualification_tool_main.cpp`'s `require_selected_model()` (real SELECTED_PAIR_CLOCK measurement gate, previously its own separate `Q15-CPUID-06_55H`-only hardcoding, found and fixed in the same pass) were all widened to accept either registered pair. `tools/q15_qualification_evidence_tool_main.cpp` gained an optional `--cpu-pair-selection-id` flag (defaulting to ADR-0043's identity for full backward compatibility) so EXT-004 evidence-building can select the correct far pair explicitly, since that tool deliberately performs no live hardware access. Four schema files' `cpu_pair_selection_id` `const` were widened to an `enum` of both identities (`q15-qualification-authorization-v1`, `q15-r-decision-input-v1`, `stage17-authorization-v1/v2`), mirroring ADR-0172's own `hardware_prefetch_mapping_id` widening; confirmed none of these four are hash-pinned anywhere in the repository (checked both the admission-policy chain and every other script that reads a schema file's own bytes), so no re-pin ceremony was needed for them.

## Implementation note 3 (Q15-R/Q15-W real MSR read/write path, commit `09aac34`)

A real, live Q15-R attempt on `cpu-prefetch-v5` (after implementation notes 1 and 2 above, and after the `runner-admission-v4`/schema follow-up's absence was confirmed non-blocking for this specific path) found a third, independent hardcoding: `src/runner/stage17_fixed_action.cpp` itself. Q15-R's own CPU-identity gate (`load_q15_phase_session`) correctly resolved the real mapping via `find_hardware_prefetch_mapping` and passed `mapping_registered=1 cpu_set_accepted=1` (confirmed directly from the real worker's own captured stderr, `S17-Q15R-CPU-DIAG`) -- but every line downstream of that gate still referenced the global `kHardwarePrefetchControlCpus` (`{0,1,26}`) and `kIntelModel55` literals directly, never the resolved `mapping`. The real fixed MSR prestate-read loop therefore tried to read CPUs `{0,1,26}` instead of this ADR's own `{0,1,8}`, failing with rule `S17-Q15R-MSR-READ` -- the real worker exiting before Q15-R even completed its H0 read, let alone reaching Q15-W.

Completed (commit `09aac34`): `Q15PhaseSession` gained an `identity` field, populated once by Q15-R's own resolved `CpuFamilyModel` and reused by Q15-W (so both halves of one real session agree on which registered mapping applies, without Q15-W re-reading CPUID or hardcoding a model of its own). The real prestate-read loop now indexes `mapping->control_cpus.value()` instead of the global constant; the Q15-R output document's `cpu_family`/`cpu_model`/`mapping_id` fields now honestly report `session.identity`/`mapping->mapping_id` instead of unconditionally claiming `06_55H`; Q15-W's prestate-CPU-order check (`parse_prestate`, which gained an explicit `expected_cpus` parameter) and its own MSR-write plan construction (`make_hardware_prefetch_plan`) both now use the same resolved mapping/identity. The four Q16a/b/c/pilot call sites of `parse_prestate`, and `PilotWholePlotControl`'s own `kIntelModel55` literal, were deliberately left unchanged -- Stage B/C remain out of scope, and nothing routes a real `06_3EH` run through them yet.

No test added: these functions (`load_q15_phase_session`, `publish_q15_r`, `q15_w`) have no dependency-injection seam around real CPUID, a pre-existing gap neither introduced nor closed by this change -- the same situation implementation note 1 already documented for the gate itself. Verified instead the same way every other change in this engagement has been: full `dev-gcc` build, identical test results (same 6 pre-existing failures), clean `format-check`/`static-analysis` for the changed file, and clean `asan-ubsan-gcc`/`tsan-gcc` sanitizer runs.

## Implementation note 4 (`LinuxHardwarePrefetchMsrBackend` CPU whitelist)

After implementation note 3's fix landed and a fresh evidence root was rebuilt against the new binary, the real Q15-R attempt's own CPUID-identity gate passed cleanly (`S17-Q15R-CPU-DIAG identity_present=1 family=6 model=0x3e mapping_registered=1 cpu_set_accepted=1`, confirmed from the real worker's own captured stderr) -- but the very next step, the real MSR prestate read, still failed with `S17-Q15R-MSR-READ`. The root cause was a fourth, independent hardcoding, this time in `src/platform/q15_msr.cpp`: `LinuxHardwarePrefetchMsrBackend::read()`/`write()` and `perform_hardware_prefetch_transition()` all gated every real I/O through a free function `allowed_cpu(cpu)` that checked only the global `kHardwarePrefetchControlCpus` constant (06_55H's own `{0,1,26}`), regardless of which mapping the caller had actually resolved. Implementation note 3 fixed every call site that *chooses* a CPU (the prestate-read loop, Q15-W's plan construction) to use the resolved mapping's `control_cpus` -- but the backend object those call sites hand the chosen CPU to still silently re-validated it against the wrong, hardcoded set underneath. CPU 0 and CPU 1 are common to both `{0,1,26}` and this ADR's own `{0,1,8}`, so the bug was invisible until the loop reached CPU 8, which `allowed_cpu()` rejected -- surfacing only as the generic `S17-Q15R-MSR-READ` failure one level up, with no indication of which specific CPU or rule actually failed, since `stage17_fixed_action.cpp` only checks `reader.read(selected_cpu)`'s boolean success, not its inner rule ID. Confirmed directly: a manual root-owned `pread` of MSR 0x1A4 on CPUs 0, 1, and 8 all succeeded on the real hardware, and `kHardwarePrefetchControlCpusV5` (this ADR's own `{0,1,8}`) was already correctly registered -- the hardware and the registry were both fine; only this one whitelist check was still wrong.

Completed: `LinuxHardwarePrefetchMsrBackend`'s constructor now takes an explicit `accepted_cpus` span, stored per instance and used by its own `read()`/`write()` instead of the global constant; `allowed_cpu()` itself became a free function parameterized on the accepted set rather than a zero-argument closure over one global array. `perform_hardware_prefetch_transition()` now resolves its own mapping from `plan.identity` and uses that mapping's `control_cpus` for the same check, rather than calling the old zero-argument `allowed_cpu()`. Every real call site in `stage17_fixed_action.cpp` (Q15-R's prestate-read loop, Q15-W's live-prestate reader/writer/verifier) now constructs its backend with `mapping->control_cpus.value()` -- the same resolved mapping those call sites already used for choosing which CPU to read, now also used for validating it. `PilotWholePlotControl` (Stage B/C, still wedded to a hardcoded `kIntelModel55` identity per implementation note 3's own scope decision) was updated only enough to keep compiling, passed the old `kHardwarePrefetchControlCpus` explicitly so its behavior is unchanged. The same bug and fix were also applied to `tools/q15_qualification_tool_main.cpp`, a separate manual CLI tool whose own `require_selected_model()` gate already recognized the registered mapping correctly but whose `read_fixed_values`/`read_fixed_cpu`/`transition` subcommands still read/wrote through the same hardcoded global array; `require_selected_model()` now returns the resolved mapping itself (`std::optional<HardwarePrefetchMapping>`) rather than a bare bool, threaded through to every call site that needs the accepted CPU set.

Tests added to `tests/q15_msr_tool_test.cpp`: `AcceptsAdr0173CpuSetAndRejectsOtherMappingsCpus` (a backend constructed with this ADR's own `{0,1,8}` set accepts CPU 8 and rejects CPU 26; a backend constructed with the old `{0,1,26}` set still rejects CPU 8 -- proving the whitelist is genuinely per-instance, not merely re-pointed to a different single global) and `AppliesAdr0173TransitionOnItsOwnResolvedMapping` (`perform_hardware_prefetch_transition` against an 06_3EH plan touching CPU 8 succeeds end to end). All five pre-existing `LinuxHardwarePrefetchMsrBackend` construction sites in that file were updated to pass the 06_55H set explicitly, keeping their own coverage of the original model's behavior unchanged. Verified: full `dev-gcc` build and `ctest` (same 6 pre-existing failures, unrelated to this change, confirmed by reproducing them against the pre-fix commit too), clean `format-check`/`static-analysis` for every changed file, and a clean `asan-ubsan-gcc` run of the `q15` test label.

Because this changed `stage17_fixed_action.cpp`'s compiled bytes a third time, it triggered the same re-pin ceremony once more (policy v51 -> v52). Still not done: the real Q15-R/Q15-W run itself, now blocked only on rebuilding the pilot-candidate bundle from this commit and admitting a fresh evidence root against it.
