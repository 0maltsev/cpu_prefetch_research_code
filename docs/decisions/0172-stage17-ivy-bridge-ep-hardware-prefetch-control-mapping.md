# ADR-0172: Stage 17 Ivy Bridge-EP hardware-prefetch control mapping

- Status: `ACCEPTED`
- Date: 2026-10-20
- Decision ID: D-172
- Classification: platform-dependent treatment mapping
- Decision owners: protocol, platform, security, and validation owners
- Protocol version: `2.0.0-pre.3`
- Supersedes: none; extends ADR-0049's model-specific mapping approach to a second CPU model
- Lifecycle gate: software mapping proposal only; dynamic evidence requires a real Q15 qualification run before any mapping is trusted for Q15-W/Q16

## Context and options

The engagement's stand changed twice in one day (2026-10-20): `cpu-prefetch-v3` (Xeon Gold 6230R, CPUID family 6 model 0x55, the only CPU ADR-0049's `INTEL-06_55H-MSR-1A4-DISABLE-0_3-v1` mapping was ever validated against) was decommissioned; a brief candidate replacement (`cpu-prefetch-v4`, Xeon Gold 6338, 06_6AH) was abandoned due to unresolved intermittent SSH connectivity, never reaching any real hardware qualification; the current real target is `cpu-prefetch-v5` (94.126.205.83, Intel Xeon E5-2667 v2 @ 3.30GHz, Ivy Bridge-EP, CPUID family 6 model 0x3E, stepping 4, 32 logical CPUs, dual-socket).

ADR-0049 is explicit that "Any mapping/model/scope/bit/probe change needs a superseding ADR and full requalification." `06_3EH` is a different CPUID model than `06_55H`, so the existing mapping's own CPUID gate (`src/runner/stage17_fixed_action.cpp`: "Q15-R requires the accepted 06_55H CPU") would reject this stand outright, and no code in this repository currently proposes an alternative.

Real research performed before drafting this (not assumed): fetched and read Intel's 64 and IA-32 Architectures SDM Volume 4 (order 335592-090US, February 2026) directly. Checked MSR 0x1A4 (`MSR_PREFETCH_CONTROL`)'s presence in the per-model MSR tables for three widely-separated generations: `06_3EH` (Ivy Bridge-EP, Tables 2-26/2-27), `06_55H` (the already-validated stand, Table 2-50), and `06_6AH`/`06_6CH` (Ice Lake-SP, Table 2-51) — absent from all three, and absent from the broad shared table (Table 2-39) that explicitly covers "1st-5th Generation Xeon Scalable" and much more. The MSR only gets an explicit per-model table entry starting at Table 2-52 (4th/5th Generation Xeon Scalable, Sapphire Rapids/Emerald Rapids), where bits 0-1 are confirmed as `L2_HARDWARE_PREFETCHER_DISABLE`/`L2_ADJACENT_CACHE_LINE_PREFETCHER_DISABLE`, matching ADR-0049's own bit description.

This consistent absence across three generations spanning 2013 (Ivy Bridge-EP) through 2021 (Ice Lake-SP) is itself evidence, not merely an absence of evidence: Intel adds a new per-model table specifically when behavior differs from prior generations, so three generations sharing no dedicated entry is consistent with (though does not prove) stable behavior across that whole lineage, with formal per-model documentation only catching up recently. Independent corroboration: this MSR is documented elsewhere (Linux kernel prefetch-disable-bit discovery patches) as "non-architectural" and has been tracked/used across many Intel platforms, including Broadwell-X, outside the SDM's per-model table structure.

A real, safe, read-only probe was also performed directly on `cpu-prefetch-v5`: `os.pread` of MSR 0x1A4 on CPU 0 (no write) returned `0x0000000000000000` — the MSR responds without a `#GP` fault (confirming it exists and is accessible on this CPU), and its value exactly matches `cpu-prefetch-v3`'s own real, repeatedly-observed H0 prestate (`0000000000000000` uniformly across CPUs 0/1/26 in every real Q15-R/Q15-W transaction this engagement has run). This is a genuine, concrete data point, not an assumption — but it is a single read of the default/reset state, not a write-then-readback-then-restore cycle, so it does not by itself confirm the bit semantics (whether setting bits 0-3 actually disables the four documented prefetch engines on this silicon) the way a real Q15 qualification run would.

Options considered:
1. Reuse `INTEL-06_55H-MSR-1A4-DISABLE-0_3-v1` unchanged, relaxing its CPUID gate to also accept `06_3EH`. Rejected: the mapping ID itself encodes and asserts a specific validated CPU model; reusing it for different silicon would make the ID dishonest regardless of how well-supported the underlying expectation is, and would silently weaken the exact-identity check ADR-0049 deliberately built in.
2. Assume identical behavior from the SDM research alone and proceed directly to real Q15-W/Q16 hardware-control use without a fresh, dedicated qualification. Rejected: the SDM research raises confidence but does not constitute dynamic evidence; ADR-0049's own lifecycle gate separates "software mapping" from "dynamic evidence at Q15" for exactly this reason, and this engagement's own standing practice never treats "the stand didn't reject it" as sufficient evidence of correctness.
3. Define a new, honestly-scoped mapping ID for `06_3EH` with the identical technical mapping (same MSR, same bits 0-3, same CPU-set pattern, same H0-preserve/H1-request-prestate-or-0x0f semantics, same independent readback/probe/restoration-verification protocol already implemented and proven on `06_55H`), and require this stand's own real Q15-R/Q15-W qualification run — using the exact same already-built regular-stream/pointer-stream probes and restoration verification ADR-0049 specified — to be the actual evidence that validates it, mirroring exactly how `06_55H` was originally validated. Selected.
4. Block entirely pending a different, out-of-band hardware verification process (e.g. vendor documentation request). Rejected as the default path for now given option 3 already provides a rigorous, real, in-engagement validation mechanism with strong built-in safety properties (independent readback, restoration verification, quarantine-on-uncertainty) — but remains available if a real Q15-R/Q15-W attempt under the new mapping fails or produces uncertain restoration.

## Decision

Propose a new, narrow mapping `INTEL-06_3EH-MSR-1A4-DISABLE-0_3-v1`, structurally identical to ADR-0049's `INTEL-06_55H-MSR-1A4-DISABLE-0_3-v1` in every respect except its CPUID gate:

- exact CPUID gate: family `06`, model `3EH` (Ivy Bridge-EP);
- exact core-scope MSR: `IA32_MISC_FEATURE_CONTROL` / `0x1A4` (unchanged);
- CPUs: the accepted near/far owner set for whichever worker-pair topology `cpu-prefetch-v5`'s own real NUMA layout uses (to be confirmed during real onboarding, analogous to CPUs `0`, `1`, `26` on the prior stand — not assumed to be the same literal CPU numbers on different hardware);
- H0: read and preserve each complete 64-bit prestate without writing (unchanged);
- H1: request `prestate | 0x0f` (unchanged — bits 0-3 disable L2 hardware, L2 adjacent-cache-line, DCU, and DCU-IP prefetchers);
- preserve bits 63:4 exactly, expose no arbitrary address/mask interface (unchanged);
- independently read back the complete requested value, run both regular-stream and pointer-stream probes, restore the complete prestate in reverse order, and independently verify restoration (unchanged — the exact same real protocol, not a relaxed one);
- reject family/model/CPU drift, missing/duplicate prestates, H0/H1 collapse, partial readback, failed probes, and uncertain restoration; restoration uncertainty quarantines the stand (unchanged).

This ADR does not itself authorize any real MSR write. Per ADR-0049's own authority boundary, actual prestate, privileged reads/writes, probes, and restoration require a distinct, exact hash-bound Q15 authorization — which in turn requires this ADR (or a revision of it) to be formally accepted by the real protocol/platform/security/validation owners before implementation proceeds. A real `cpu-prefetch-v5` Q15-R/Q15-W run under this new mapping, completing with `restoration_verified: true` and passing probes, is the dynamic evidence that would actually confirm (not merely support) this mapping's correctness for this CPU generation — exactly as the original `06_55H` mapping was confirmed by its own first real Q15-R/Q15-W run on `cpu-prefetch-v3`, not by document review alone.

## Evidence and effects

- Real SDM research: Intel 64 and IA-32 Architectures SDM Volume 4, order 335592-090US, February 2026, Tables 2-26, 2-27, 2-39, 2-50, 2-51, 2-52 — read directly this session, not recalled from training data.
- Real, safe, read-only MSR 0x1A4 probe on `cpu-prefetch-v5` CPU 0: value `0x0000000000000000`, no fault — matches `cpu-prefetch-v3`'s own real observed H0 prestate across all three real Q15-R/Q15-W transactions this engagement has run.
- Existing hashed candidate inventory and CPUID evidence for `cpu-prefetch-v5` (`/proc/cpuinfo`: family 6, model 62, stepping 4) — this identifies the candidate but, consistent with ADR-0049's own standard, does not replace a fresh Q15 readback.

Scientific effect: proposes extending (not changing the meaning of) the already-registered H0/H1 factor to a second CPU model, pending real confirmation. Compatibility effect: model, MSR, mask, CPU set, prestate, readback, probes, restoration, tool hash, and evidence schema remain qualification identity, now parameterized by model rather than hardcoded to one — this is a real code change (the CPUID gate in `src/runner/stage17_fixed_action.cpp`, the `kHardwarePrefetchMappingId`/`kIntelModel55` constants in `include/cpu_prefetch/platform/platform.hpp`, and every schema `const` currently pinned to `INTEL-06_55H-MSR-1A4-DISABLE-0_3-v1`) that has not yet been made and should not be made before this ADR itself is accepted. Owner: platform/protocol. Deadline: before any real Q15 action is attempted on `cpu-prefetch-v5`. Any further mapping/model/scope/bit/probe change needs its own superseding ADR and full requalification, same as ADR-0049's own rule.

## Authority boundary

This document proposes a mapping and the real evidence gathered to support proposing it; it does not itself approve the mapping, authorize any code change, or authorize any real prestate read, privileged write, probe, or restoration on `cpu-prefetch-v5`. Acceptance by the real protocol/platform/security/validation owners, followed by the exact hash-bound Q15 authorization and distinct operational authorities ADR-0049 already requires, remain necessary before any real hardware operation under this mapping may proceed.

## Implementation note (post-acceptance)

Accepted and implemented: `include/cpu_prefetch/platform/platform.hpp` gained a per-model registry (`kHardwarePrefetchMappings`, `HardwarePrefetchMapping`, `find_hardware_prefetch_mapping`, `is_accepted_hardware_prefetch_mapping_id`) replacing the single hardcoded `kIntelModel55` equality check; `src/platform/platform.cpp`, `src/platform/q15_msr.cpp`, `src/runner/stage17_fixed_action.cpp`, and `tools/q15_qualification_tool_main.cpp` were updated to use it. The new `06_3EH` entry's `control_cpus` is deliberately `std::nullopt` — no CPU set is assigned, and every code path that needs one (`make_hardware_prefetch_plan`, the production Q15-R gate, the qualification tool) fails closed with a distinct rule id (`HWP-CPU-SET-UNASSIGNED` / `S17-Q15R-CPU-SET`) naming the still-required, separate pair-identity ADR (the same kind ADR-0043 provided for `06_55H`), per this ADR's own authority boundary. Twelve schema files had their `mapping_id`/`cpu_model`/`cpu_model_hex` `const` widened to `enum` to admit the new mapping id alongside the old one. Seven of those were edited in place (additive; no version bump, since no required-field shape changed and no historical record pins their exact bytes). The other five (`hardware-prefetch-qualification-v1`, `stage17-calibration-hardware-state-v1`, `stage17-pilot-hardware-state-v2`, `stage17-pilot-plan-v4`, `stage17-q15-r-output-v3`) are each transitively hash-pinned, by unversioned path, inside dozens of frozen historical `stage17-operational-evidence-admission-policy-vNN.json` generations (v11 through v49) and the repository's own immutable genesis-journal self-test (`check_stage17_operational_successor.py`, which resolves to a frozen v22-era policy) — editing them in place would have silently invalidated those historical records' own hash pins, i.e. rewritten history. Those five were therefore left byte-identical and superseded instead by new sibling files (`-v2`/`-v2`/`-v3`/`-v5`/`-v4` respectively) carrying the widened content; only the currently-active consumer (`tools/check_hardware_prefetch_schema.py`) was repointed at the new sibling. `tests/platform_model_test.cpp` gained direct coverage of the registry, the fail-closed path (including the empty-prestate hazard the `std::optional<span>` design specifically guards against), and the membership helper; all pre-existing `06_55H` tests (`platform_model_test.cpp`, `q15_msr_tool_test.cpp`) were re-verified passing unmodified. `src/runner/stage17_fixed_action.cpp`'s compiled bytes changed, triggering this repository's established re-pin ceremony (new operational-evidence-admission-policy generation, v49->v50) exactly as ADR-0171 required for the Q16b fix. The full `qualification-schema-check` sweep (37 scripts) and `protocol-check`/`schema-fixture-check`/`canonical-check`/`runner-schema-check` all pass after this change; the one remaining failure in `check_stage17_operational_successor.py --self-test` (a stale `src/runner/stage17_fixed_action.cpp` binding inside that same frozen v22-era policy) was confirmed present on a clean pre-ADR-0172 tree via `git stash` and is therefore pre-existing and out of scope here.

Still explicitly not done by this change, matching the authority boundary above: no CPU set, no real Q15-R/Q15-W authorization, and no real MSR operation exists for `06_3EH` yet. A separate, topology-evidence-backed pair-identity ADR for `cpu-prefetch-v5` (the ADR-0043 equivalent for this stand) remains required before any real hardware action under this mapping can proceed.
