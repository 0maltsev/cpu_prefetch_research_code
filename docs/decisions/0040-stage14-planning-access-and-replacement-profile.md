# ADR-0040: Stage 14 planning, access, and replacement profile

- Status: `ACCEPTED`
- Date: 2026-08-21
- Classification: Implementation-owned orchestration and compatibility profile
- Decision owners: Repository owner; protocol/validation owner; block-planning owner
- Protocol version: `2.0.0-pre.2`
- Supersedes: None
- Lifecycle gate: Stage 14 software closure; no calibration, pilot, or confirmatory execution authority

## Context and scientific constraints

The imported protocol fixes the 180-cell Stage A product, two hardware-state
whole plots, three immutable block roles, common-pool count equations,
precision families, access chronology, and complete-block replacement rule.
It does not prescribe a C++ API, block-ID grammar, canonical plan hash profile,
or in-memory access-policy representation. Concrete repetition counts, seed
values/subspaces, authorities, platform identity, and replacement budget remain
prospective evidence and cannot be generated by the implementation.

## Options considered

1. Treat a block plan as a generic list and rely on JSON Schema cardinality.
2. Infer role, identity, and seed membership from directory/name conventions.
3. Build a typed expected Cartesian product, consume explicit role namespace
   and pre-derived-key catalogs, and validate the complete cross-record graph.

Options 1 and 2 cannot prove scientific completeness or prevent path- and
outcome-dependent orchestration. Option 3 preserves the imported model and
keeps every external freeze input explicit.

## Decision

Accept `STAGE-A-BLOCK-PHILOX-FISHER-YATES-v1` for deterministic planning:

- consume three explicit pre-derived Philox keys per block, using the accepted
  Philox/Fisher-Yates implementation without deriving or inventing a master
  seed;
- randomize the two-state whole-plot order, then independently randomize the
  90 registered cells within each state;
- assign arrival seeds by placement/working-set/load, persistent event seeds by
  placement/working-set, and linked-only node seeds by placement/working-set;
- form a block ID from canonical protocol version, Stage A, platform ID, build
  ID, immutable role, and block ordinal, never from a filesystem path; and
- hash the full imported block document with
  `BLOCK-PLAN-JCS-I64-ZEROSELF-SHA256-v1`.

Accept a repository-owned, offline access ledger that validates immutable
record IDs, zero-self hashes, normalized nondecreasing UTC chronology,
predecessor hashes, exact block roles/namespaces, six H3 contexts, authority
assignments and explicitly evidenced role overlaps. It exposes only a
fail-closed access decision; it does not open files or expose outcome bytes.
The transition to `TRAINING_OPEN` must additionally bind the fixed family and
candidate/context registries, prospective counts, tie-break/bootstrap/schema
identities, and exact hashed precision inputs; a state label without this
evidence is rejected. Every role transition names its complete applicable
block set rather than a convenient subset.

Accept `SELECTION-PAYLOAD-JCS-I64-SHA256-v1` over exactly the selection map,
training artifact references, and registered selection-rule version. The
record's separate zero-self hash binds this payload checksum to governance and
chronology. Replacement authorization must bind the frozen budget artifact by
both ID and SHA-256.

Accept fixed registries for the seven H1 contrasts, twenty H2 contrasts, 270
unordered H3 training pairs, 540 ordered pre-selection validation comparisons,
and 54 selected-minus-alternative reported comparisons. Count evaluation
requires explicit prospective evidence and implements only the imported
formulas/minima/ceiling.

Accept replacement generation only after a retained invalid required run,
matching invalidating failure, exact authorization/failure/budget links, and
available `R_replacement_max`. A replacement is a new full 180-cell plan with
new ID, ordinal, role-compatible seed subspace, and random order. Exhaustion
returns `STUDY_UNRESOLVED`; no cell-repair API exists.

## Evidence

- Imported block-plan and freeze-record schemas explicitly delegate Cartesian
  completeness, role/seed membership, chronology, authority segregation,
  budget, and lineage to semantic validation.
- ADR-0025/0026 already freeze Philox4x32-10 and unbiased descending
  Fisher-Yates; Stage 14 reuses those reviewed primitives.
- Synthetic unit/property/schema tests cover 32 distinct key sets, structural
  mutations, exact precision families, access violations, amendments,
  authorized replacement, valid `FULL`/low-tail rejection, branching, and cap
  exhaustion.

## Consequences and compatibility

Scientific effect: none. The profile proves the imported product and access
rules and refuses unresolved values. It neither selects counts/seeds nor reads
outcomes during plan generation.

Compatibility effect: the block-ID preimage fields, permutation key roles,
seed-sharing map, plan hash suite, fixed family registries, access-role map, and
selection-payload hash/replacement lineage checks are version identity. Plans from another profile
must use a new suite/version and cannot be silently reinterpreted.

## Verification and acceptance tests

Require exact product/ordinal/whole-plot proof, deterministic reproduction,
role namespace and seed non-overlap, pool counterbalance, precision formulas,
schema fixtures, full access chronology and negative access, complete-block
replacement, amendment lineage, sanitizer matrices, formatting/static checks,
and full regression. All evidence is synthetic and non-performance.

## Rollback or supersession

An identity preimage, randomization step, key role, seed-sharing rule, hash
profile, fixed registry, access mapping, or replacement rule change needs a new
profile and superseding ADR. Existing plans and ledgers remain immutable.

## Protocol-amendment assessment

No amendment is required: the implementation fills only explicitly delegated
engineering seams and preserves every imported scientific rule. A new factor,
changed family/count equation, outcome-dependent generation, cell replacement,
role reinterpretation, or weaker sealing rule requires protocol-owner review
and normally a versioned amendment.
