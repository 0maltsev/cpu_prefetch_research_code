# D318: S180 prospective sizing and parent plan preparation

Accepted engineering implementation under the owner's D310 S180 approval. This
closes a concrete pre-launch sizing gap and fixes an R1 input-contract defect.
No experiment, window, count, seed, scientific method or immutable protocol is
changed. The qualified parent/profile and actual signed scoped admission remain
required; this step does not implement or exercise a live launch.

## R1 registered-policy correction

D317's parser assigned the accepted freeze hash as distance evidence to both R1
and R2. The existing mapped-service native contract requires R1's registered
one-line policy to carry an empty calibration evidence ID. Consequently an R1
capture could pass the family declaration checks but fail its mandatory native
layout check before measurement. No pilot was launched with that parser.

R1 now carries one line and no calibration credit; R2 keeps its accepted distance
and exact descriptive freeze binding. The family validator also rejects an R1
calibration-evidence ID before any backend callback. The source is the existing
registered policy, not a new scientific decision or favorable replacement run.

## Sizing without fabricating a prepared mapping

The previous native pilot layout API requires actual live shared mappings and
original loaded source spans. It could not calculate a prospective resource
plan without first preparing the stand. A separate API now computes layout from
explicit declared counts and the same service/package/arena/raw-buffer rules.
It creates no schedule vectors, data mappings, threads or hardware observations.

The private pilot layout uses the declared offered counts. Actual execution
continues to verify those counts against the original loaded spans and to check
live shared owner mappings and the frozen node-address pattern. Shared native
envelope arithmetic is factored once: execution still enters through its strict
live checks; the prospective API supplies only declared region sizes. The Core
type and measured worker loops are unchanged. A layout is not a runtime capability.

Tests compare every layout field against actual prepared software mappings for
R0/R1/R2/L0/L1. A billion declared arrivals per phase is sized without allocating
the represented arrays. Live/inline inputs, invalid counts, wrong owners and
incorrect R1 evidence cannot enter the prospective API. These tests establish
software sizing, not real NUMA placement or platform/performance qualification.

## Separate full-family declaration contract

`cpu-prefetch-stage17-s180-sizing-plan/1` is separate from the execution plan.
It has no caller-authored expected layouts or source descriptors. The same parser
derives scientific identity from the exact approved blueprint, and the same
declaration validator checks all180 captures, six contexts, common schedules,
explicit native limits and necessary aggregate memory/output/time minima.

Source count basis must explicitly be `EXACT_DECLARED_COUNTS` or
`PROSPECTIVE_UPPER_CEILINGS`. An unmaterialized original source is null in a sizing
document; no hash, descriptor, hardware value or generated observation is invented.
The execution parser rejects that sizing schema and retains its separate complete
physical source checks. The native controller still calls only execution validation.

The read-only CLI `--describe-stage17-s180-layouts-v1 FILE` consumes at most16MiB
and emits all180 complete layouts and six shared footprints. It binds the input
hash, actual executed binary hash and compiled source/dirty identity. Its result
explicitly says requested geometry, declared counts, source bytes unchecked,
no session admission and no execution/Stage18 authority. It does not establish
fresh platform values, source provenance or a successful resource admission.

## Parent planning seam

The parent planner pins the exact worker image and sizing bytes into sealed
descriptors, invokes only that fixed description command under a finite deadline
and checks the returned actual binary/source/input identity. It checks frozen
execution order, all18 common source pairs, disjoint schedule/artifact identities
and equality of paired source coordinates. There is no arbitrary command or
experimental execution path in this module.

A collection-plan candidate can be assembled only from exact declared counts
and explicit original artifact bindings. A ceiling document cannot become a
collection plan. Complete expected layouts come from the actual native report;
the caller cannot inject them. The candidate's canonical hash and preparation
proof remain metadata, with source-byte verification, namespace reservation,
signed admission, launch readiness and execution authority explicitly false.

The planner derives necessary native shared/private memory, original-vector
retention/transient limits, output reservation and native family watchdog from
that same declaration. The full collection bound counts one native process plus
180 brokers and24 codec processes per complete capture:4,501 in total. The
separately charged source memfds and unknown external preparation/qualification/
analysis/runtime resources are visible; these minima are not a complete EXT009
or whole-day feasibility proof. No compression credit is applied to hot buffers.

The historical pilot declares60seconds recovery. This discovery does not turn
that historical declaration into fresh stand verification or choose a recovery
value in the implementation: the current prospective input must still bind its
explicit recovery and complete operational estimate before admission.
